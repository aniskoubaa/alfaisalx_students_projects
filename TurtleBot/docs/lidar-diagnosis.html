TurtleBot 4 · incident record · TB-02

Lidar diagnosis

On 2026-10-03 the lidar spun but the Raspberry Pi could not see it on USB, so there was no /scan. On 2026-10-04 the USB cable was reseated, and each layer from USB up to scan data was checked. This page records the checks and the values measured.

Status Resolved 2026-10-04 Root cause loose USB connection Software changes none Times robot clock, EDT (UTC-4)

Verdict: lidar fixed by reseating the USB cable

The lidar and its driver work. The USB data connection between the lidar and the Pi was loose. After the user reseated the cable (same cable, same port) and booted the robot at about 11:44, all four layers passed: the CP210x USB bridge enumerated, /dev/RPLIDAR appeared, the driver reported health 0, and off the dock /scan ran at 7.75 Hz with 720 beams.

"No /scan while docked" is the TurtleBot 4 power saver, not a fault.

Symptoms on 2026-10-03

  • The lidar spun, so it had power.
  • lsusb listed no Silicon Labs CP210x device, docked or undocked.
  • /dev/RPLIDAR did not exist; the driver log said cannot bind to the specified serial port '/dev/RPLIDAR'.
  • A full power cycle (Pi shut down, base off and on) did not help.

The lidar's motor and its USB data link are separate. A spinning lidar that is missing from lsusb points at the data connection: cable, connector or the lidar's USB adapter board.

02

Diagnosis flow

Check from the bottom up and stop at the first layer that fails. All checks are read only and run in a terminal on the robot (ssh ubuntu@turtlebot4.local).

  1. Physical and USB pass

    Is the USB bridge enumerated and is the device link there?

    lsusb | grep -i -E "silicon labs|cp210"
ls -la /dev/RPLIDAR /dev/ttyUSB0

    2026-10-04: 10c4:ea60 Silicon Labs CP210x UART Bridge; /dev/RPLIDAR -> ttyUSB0. If this fails: reseat both ends, then try another port, another cable, then the lidar on a laptop (TB-02 steps).

  2. Driver pass

    Did rplidar_composition open the port and read the device?

    journalctl -u turtlebot4 -b --no-pager | grep -i rplidar

    2026-10-04: started with S/N, firmware 1.29, hardware revision 7, health status 0, scan mode Sensitivity.

  3. ROS graph pass

    Is /scan advertised, and in the expected environment?

    ros2 topic info -v /scan

    2026-10-04: 1 publisher (reliable), subscriber turtlebot4_diagnostics (best effort).

  4. Data, off the dock pass

    Undock first: the lidar is stopped on the dock. Then measure rate and content.

    ros2 topic hz /scan
ros2 topic echo --once --full-length /scan
python3 ~/robot_code/clearance_check.py 0.6; echo "exit code $?"

    2026-10-04: 7.75 Hz, 720 beams, 72 % valid; clearance_check.py exit 0.

04

Mount and front sector

The lidar is mounted turned +90° about the vertical axis. Transform base_link → rplidar_link: translation (−0.040, 0, 0.193) m, yaw +90°. A beam at laser angle a points at robot angle a + 90°, so straight ahead of the robot is laser angle −90°, and the ±30° front sector is laser angles −120° to −60° (about 120 beams; 78 were valid in the scan above). clearance_check.py and motion_shapes.py read this offset from TF.

05

Dock power saver

The TurtleBot 4 node stops the lidar while the robot is docked, to save power. On the dock /scan still has its publisher but carries no messages. This is expected and is the first thing to rule out when /scan is silent.
