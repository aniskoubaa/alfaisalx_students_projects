Motion simulator

Click a shape and watch how motion_shapes.py drives it: the plan (dashed), the path actually driven (solid), the speed commands 20 times a second, and the safety checks that stop it. The simulator runs the same planner and control rules as the real program in your browser. Nothing here moves a robot.

02
How the program decides

      
    
        
  1. 
          
    1. Plan
    
          
    The shape becomes a list of segments: drive straight (a distance), turn in place (an angle, + is left), or drive a full circle. A square is 4 × (straight, turn left 90°). A figure eight is a left circle then a right circle, radius 0.20 m. Each segment gets an expected time and a timeout of 2 × expected + 5 s. If the whole plan needs more than 120 s the program refuses to start.
    
        
    2. 
        
  2. 
          
    2. Control loop, 20 times a second
    
          
    Every 50 ms the program reads the robot's position and heading from odometry (/odom) and computes a speed command for the current segment:
    
          
      
            
    • Straight: v = max(0.03, min(speed, 1.0 × remaining)), and a steering correction w = clamp(1.5 × heading error, ±0.3) to hold the heading. Done when less than 1 cm remains.
      • 
            
    • Turn in place: w = sign × max(0.15, min(turn_speed, 1.5 × |remaining|)) towards an absolute target heading, so an overshoot is turned back. Done within 1.5°.
      • 
            
    • Circle: w = v / r with r = 0.20 m, lowered if it would exceed the turn speed, then slowed near the end like a turn.
      • 
          
    
          
    Between segments the robot stands still for 0.5 s. That is why every shape takes longer than distance divided by speed.
    
        
    3. 
        
  3. 
          
    3. Safety checks, every cycle
    
          
    The STOP file and Ctrl+C, hazards reported by the base (bump, cliff, wheel drop), odometry too old, lidar obstacle closer than 0.25 m ahead (only while driving, see below), and the timeouts. Any of them stops the robot and ends the program with "ABORTED". The simulator implements the lidar, odometry and timeout checks; bump, cliff and the stall check are not simulated.
    
        
    4. 
      

      
Full explanation with the source: motion-program-design.html.

    


    

      
03
Lidar stop zone

      
The orange wedge on the robot is the stop zone: anything the lidar sees within ±30° of straight ahead and closer than 0.25 m stops the robot. The very faint wedge beyond it is the part of the scan the program looks at (the lidar itself reaches 12 m). The lidar sits 4 cm behind the robot's centre, so the 0.25 m is measured from there.

      
To see it: press Play, then click the floor ahead of the robot while it drives (or press Drop a box ahead). When the box enters the zone the robot stops and the readout shows the real message, ABORTED: obstacle 0.2x m ahead (limit 0.25 m). The same check runs on circles. Before starting, the program also checks that the first leg is clear (the straight plus 0.25 m): a box placed in the way before you press Play gives ABORTED: path not clear.

      
Turning in place does not check the lidar. The program only checks the lidar when the segment is not a turn. A round robot that spins on the spot sweeps the same circle of floor it already covers, so no new floor comes under it: there is nothing new to hit, and a person walking up to the side would not be caught by a forward-only check anyway. Try it: choose rotate, press Play, and drop a box in front. The robot keeps turning. (A bump is a different safety check, done by the base.)

    


    

      
04
Odometry dropout

      
The program has no camera or map: it knows where it is only from the wheel odometry the Create 3 base publishes on /odom. Press Odometry dropout 0.8 s while the robot is driving:

      
    
        
  • If the newest odometry is older than 0.3 s, the program sends zero velocity and waits. The readout shows held still for N control cycles waiting for odometry.
    • 
        
  • If there is no odometry for more than 2.0 s it aborts: ABORTED: odometry is stale (none for 2.0 s). Use the 2.5 s button.
    • 
      

      
This really happened on 2026-10-04. The Create 3 base sometimes paused /odom for 0.4 to 2 s while driving. The triangle run was held still three times (11, 8 and 1 control cycles) and still finished. The figure eight finished its first circle, then aborted safely when one gap reached 2.0 s. See test-results.html and ROADMAP TB-15. In the simulator the robot keeps moving for the first 0.3 s of a dropout (it has not noticed yet), then stands still.

    


    

      
05
Simulation vs the real robot

      
The simulated columns are computed live in your browser at the default settings (side 0.40 m, 0.10 m/s, 0.5 rad/s, no realism, no dropouts). The real runs are from 2026-10-04. Errors are odometry end errors (what the robot believed), not measured on the floor.

      

        

          
ShapePlan saysSimulatedReal robotSim odometry end errorReal odometry end error

          
        

      

      
Why the real runs are slower than the plan. The plan (distance / speed + angle / turn speed + 0.5 s pauses, about 33 s for the square) assumes full speed all the way. The program does not run at full speed all the way:

      
    
        
  • Slow-down near each goal. The last 10 cm of a straight and the last 0.33 rad (about 19°) of a turn are driven slower, down to 0.03 m/s and 0.15 rad/s. This alone adds about 0.9 s per straight and 0.6 s per turn. The simulator reproduces it, which is why it lands close to the real time (square 38.8 s simulated, 39 s real).
    • 
        
  • Pauses. 0.5 s after every segment, including the last, is already in the plan.
    • 
        
  • Start-up and the base. The simulator changes speed instantly; the real base has to speed up and slow down, and the program's first cycles wait for the first odometry. The leftover difference (for example triangle: 32 s simulated, 37 s real) is mostly the three odometry holds on that run. Not measured separately.
    • 
      

      
The simulated end errors are small because the simulator measures with the same odometry it steers by: the stop rule (1 cm, 1.5°) is all that is left. Tick Add realism in the simulator to give the wheels a small slip and scale error: the odometry still says "almost back at the start" but the solid line on the floor ends somewhere else. That is why the program prints "odometry only; the real error is larger, measure it on the floor". The size of the slip here is invented for illustration, it is not measured from the robot.

    


    

      
06
Try it on the robot

      
The real program moves the robot. First: undock it (how), clear about 1 m of floor all round, and keep a person next to it. Speed is capped at 0.15 m/s. Run these on the robot (in the SSH session, see HOW-TO-CONNECT.md). From a non-login shell, run source /etc/turtlebot4/setup.bash first.

      

        

          
1. Dry run first: checks everything, prints the plan, never moves
python3 ~/robot_code/motion_shapes.py square --dry-run

          
2. The real run, detached so a Wi-Fi drop does not kill it
setsid nohup python3 ~/robot_code/motion_shapes.py square --yes > ~/robot_code/shapes.log 2>&1 &
tail -f ~/robot_code/shapes.log

          
Options: --side 0.4, --speed 0.1, --turn-speed 0.5, the same numbers as the sliders. Shapes: square, triangle, rotate, back_and_forth, figure_eight. Star, polygon and circle are in more_shapes.py, which has not been run on the robot yet.

        

        

          
Three ways to stop it (the robot stops, the program exits)

          
a. Ctrl+C in the terminal running it (not available for a detached run)

          
b. From another terminal on the robot (delete the file afterwards or the next run refuses to start)
touch ~/STOP
rm ~/STOP

          
c. From another terminal on the robot
pkill -INT -f motion_shapes.py

          
Or pick the robot up: lifting it makes the wheels stop. Details and exit codes: examples README.

        

      

    


    

      
07
What is not simulated

      
    
        
  • The base speeds up and slows down gradually; the simulator jumps to the commanded speed instantly.
    • 
        
  • Bump, cliff, wheel-drop and stall checks, the STOP file and signals, the 1 s start-up listen, and the lidar-stale check.
    • 
        
  • Lidar scans arrive 7.7 times a second on the robot; the simulator refreshes the box distance every 0.13 s. Boxes are perfect squares seen by 121 beams (0.5° apart), with no noise.
    • 
        
  • The slip in "Add realism" is a made-up size. It shows that the floor and the odometry disagree, not by how much on this robot.
    •
