TurtleBot 4 · design note · examples/motion_shapes.py

Motion program design

motion_shapes.py drives the robot along a square, triangle, in-place rotation, back-and-forth or figure eight. It plans each shape as a list of segments, closes the loop on wheel odometry, and wraps the motion in several independent safety checks. This page explains how it works and why, for anyone who wants to change it or write a similar program.

One ROS 2 node, written in Python with rclpy. It runs on the robot, publishes geometry_msgs/msg/TwistStamped on /cmd_vel (this robot does not accept plain Twist there), and reads /odom, /scan, TF, /dock_status and /hazard_detection. Nothing in it changes the robot's configuration.

02

Architecture

Run sequence

  1. Clamp the settings to the caps and build the plan. Refuse if the plan needs more than 120 s or ~/STOP exists.
  2. Wait up to 30 s for /odom and /dock_status. Refuse if the robot is docked.
  3. Wait up to 30 s for /scan, read the lidar yaw from TF, and check the path ahead: first leg + 0.25 m clear (radius + 0.25 m for a circle; nothing for a turn).
  4. Listen 1 s for hazards with a clean slate.
  5. Dry run: stop here. Otherwise ask "Type yes" (or require --yes when detached).
  6. Drive each segment, stand still 0.5 s between segments, then print planned against odometry end pose.
03

Segment planner

Every shape is a list of three kinds of segment: straight (distance in m), turn in place (signed angle, + is left) and arc (a full circle, + left, − right, radius in m). Expected time is distance/speed or angle/turn rate; each segment's timeout is 2 × expected + 5 s. Values below are for the defaults (side 0.40 m, 0.10 m/s, 0.5 rad/s, 0.5 s pause after each segment).

ShapeSegmentsExpected per segmentTimeout per segmentPlan total
square4 × (straight 0.40 m, turn +90°)4.0 s / 3.1 s13.0 s / 11.3 sabout 33 s
triangle3 × (straight 0.40 m, turn +120°)4.0 s / 4.2 s13.0 s / 13.4 sabout 28 s
rotateturn +360°12.6 s30.1 sabout 13 s
back_and_forthstraight 0.40 m, turn +180°, straight 0.40 m, turn +180°4.0 s / 6.3 s13.0 s / 17.6 sabout 23 s
figure_eightarc +360° r 0.20 m, arc −360° r 0.20 m12.6 s30.1 sabout 26 s

Headings are tracked as a running sum of small yaw changes (HeadingTracker), not as the raw yaw, so a 360° turn ends at +360° instead of wrapping to 0°. Turn targets are cumulative (the planned heading after all turns so far), so small errors in one turn are corrected by the next instead of piling up.

back_and_forth turns round instead of reversing: the Create 3 limits driving backwards and the lidar stop covers only the front.

05

Closed-loop controller

Each segment is measured from where it started. The controller is a simple proportional law with limits; no integral term, so it cannot wind up during an odometry hold.

Straight, with heading hold

remaining = distance − distance travelled since the segment start.

v = clamp(1.0 · remaining, 0.03, speed)
w = clamp(1.5 · heading error, ±0.3)

Done within 1 cm. The heading error is planned heading minus summed heading, so the robot steers back onto the planned line direction.

Turn in place

remaining = planned cumulative heading − summed heading (signed).

w = sign(remaining) · clamp(1.5 · |remaining|, 0.15, turn speed)

Done within 1.5°. Because remaining is signed, an overshoot turns back.

Arc (circle)

remaining = |angle| − turned so far in the circle's direction.

w = clamp(1.5 · remaining, 0.15, w nominal)
v = w · radius

Slowing down keeps v / w = radius, so the circle stays round. Nominal w = speed / radius, limited to the turn speed by lowering v.

The slow-down terms make the robot creep over the last 10 cm or 10° or so, which keeps overshoot small without needing a stop-and-correct phase.

06

The 20 Hz loop

Each cycle first spins ROS until the next 50 ms tick (callbacks run here and update the stored state), then does all the work at once: safety checks, segment timeout, odometry hold, command, publish, stall check. Ticks are scheduled from a fixed start time, so a slow cycle does not shift the following ones.

What happens at each tick

  1. check_safety: stop request, ~/STOP, hazard, odometry older than 2.0 s, scan older than 1.0 s, obstacle (forward kinds only), total timeout.
  2. Segment timeout.
  3. Odometry older than 0.3 s: publish zero velocity, reset the stall reference, skip to the next tick.
  4. Compute remaining distance or angle; leave the segment if within tolerance.
  5. Publish (v, w) as TwistStamped with the current stamp and frame_id = base_link.
  6. Stall check: if odometry has not moved 5 mm or 1° for 3 s while commanding motion, abort.
07

Safety layers

Defence in depth: each layer works on its own, so one failing sensor or bug does not leave the robot unguarded. Grey: before moving. Orange: while moving. Red: on every exit. The last line of defence is physical: a person next to the robot, and the Create 3's own wheel-drop and cliff stops.

1Speed caps · 0.15 m/s, 1.0 rad/s, side ≤ 1.0 m, plan ≤ 120 sat start, whatever the optionsclamp / refuse
2Pre-checks · odometry and dock status present, not docked, scan present, path ahead clear, no hazard, no ~/STOPbefore the first commandrefuse (exit 2)
3Human confirmation · "Type yes", or --yes when detachedbefore the first commandrefuse
4Lidar front stop · anything < 0.25 m within ±30°straight and arc segmentsabort
5Hazard stop · bump, cliff, wheel drop, stall, proximity from the baseevery cycleabort
6Odometry hold / stale · hold at 0.3 s, abort at 2.0 s; scan stale at 1.0 severy cyclehold / abort
7Stall · no odometry progress for 3 s while commanding motionevery cycleabort
8Timeouts · segment 2 × expected + 5 s; whole shape 120 severy cycleabort
9Stop requests · Ctrl+C, SIGTERM, ~/STOP fileevery cyclestop (exit 130)
10Finally: zero velocity · 0.5 s burst of zero commandsevery exit pathalways

The lidar stop is off during in-place turns on purpose: the round base sweeps no new floor when it turns about its centre, and a check there would mostly trigger on objects at the robot's sides. Stale-scan and every other check stay on during turns.

Finding: /odom pauses at motion start

The first real square run (2026-10-04) aborted after about 1 s with odometry is stale (none for 0.5 s). The robot was then examined without motion, and with one short instrumented move.

The header stamps show the same gap as the arrival times, so the base stopped producing odometry; messages were not just delayed on the Pi.

The two fixes

VersionRuleOutcome
OriginalAbort if odometry older than 0.5 saborted square after about 1 s
Fix 1Abort if older than 1.0 sdone square, rotate, back_and_forth; aborted triangle on a 1.0 s gap at a segment change
Fix 2 (current)Older than 0.3 s: send zero velocity and wait; abort only if older than 2.0 s. A hold resets the stall timer and is reported as "held still for N control cycles"in use Triangle completed through three holds (11, 8 and 1 cycles); a figure eight still aborted on a 2.0 s gap, with the robot standing still the whole time. See test results

Why hold instead of driving on: during a gap the program does not know where the robot is, so driving on blind could overshoot a segment end. Holding costs a fraction of a second and keeps the distance and angle checks honest. The base also limits motion itself if /cmd_vel stops, but the program does not rely on that.

Stopping and exit codes

Ctrl+C in the program's terminal, touch ~/STOP or pkill -INT -f motion_shapes.py from another terminal on the robot each stop the robot within one cycle; the program then sends zero velocity for 0.5 s and exits. Delete ~/STOP afterwards or the next run refuses to start. If software does not respond, lift the robot (wheel drop stops the wheels).
