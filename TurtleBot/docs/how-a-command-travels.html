How a command travels

When a program says "drive", the command crosses ROS 2 on the Pi, a program that forwards it, a USB cable and the small computer inside the base before the wheels turn. The answer comes back the same way, as odometry. This page follows that path, then explains the pauses we found on it and what the lab did about them.

Measured the pauses, the join test, 10 supervised motion starts (2026-10-24) Inferred the cause (discovery load on the base) Not proven that change R19 fixed it (one run)

  1. Your program publishes a velocity command

    A Python program on the Pi decides how fast to drive and turn, and sends that as a message.

    Details
    • Topic /cmd_vel. Message type geometry_msgs/msg/TwistStamped with frame_id = base_link. This robot does not accept a plain Twist there (motion program design).
    • The example program motion_shapes.py is one ROS 2 node written with rclpy. Its control loop publishes once per cycle, CONTROL_RATE 20 Hz (examples README).

  2. ROS 2 delivers it on the Pi

    ROS 2 hands the message to whoever listens to that topic. The delivery layer is called DDS.

    Details
    • Fast DDS (rmw_fastrtps_cpp), ROS domain 0, simple discovery: every new ROS 2 program announces itself by multicast on every network interface, including the one to the base (ROADMAP, TB-25 step 3, read on 2026-10-24).

  3. The republisher picks it up

    A helper program on the Pi, create3_republisher, is the go-between for the Pi and the base.

    Details
    • Started by turtlebot4_bringup/launch/robot.launch.py with robot_namespace: _do_not_use. It republishes battery_state, dock_status, imu, odom, tf, tf_static, wheel_status and others, and subscribes to cmd_vel among four topics. This is the Jazzy default configuration. Seen at 18.8 % of one core on one reading.

  4. It crosses the USB cable

    The Pi and the base are joined by a USB cable that works as a small network of two computers.

    Details
    • Pi 192.168.186.3 to base 192.168.186.2. Ping across it has a median of 0.5 ms (TB-25).

  5. The base firmware receives it

    The base is a separate small computer from iRobot with its own program. It reads the command.

    Details
    • Firmware I.0.0.FastDDS (ROS 2 Iron), the newest Create 3 release. Its ROS namespace is /_do_not_use; you never use that name yourself, the republisher does.
    • Idle and docked, the base's CPU is about half used (mean 52 to 56 %, from its own log). Remember this for section 02.

  6. The motors turn the wheels

    The base turns the command into wheel speeds and the robot moves.

    Details
    • How the firmware does this is iRobot's code and is not described in this repo. The lab's programs cap speed (see the safety checklist) and stop on the bumpers and the lidar.

  7. Sensors measure what actually happened

    Wheel encoders count how far each wheel turned. The IMU senses turning and shaking.

    Details
    • Published as /wheel_status and /imu (the timing recorder watches both).

  8. The base publishes odometry

    From the sensors the base works out its position and heading and sends that as odometry, about 20 times a second.

    Details
    • /odom, nav_msgs/msg/Odometry, normally 20 Hz. The health check warns below 15 Hz.
    • This is the stage that pauses in TB-25: all base topics stop together and their header stamps stop too.

  9. Back over the cable to the republisher

    The odometry crosses the same USB link, and the republisher puts it on the Pi's ROS 2.

    Details
    • The same address pair, in the other direction. The timing recorder measures the gap between two arrivals of /odom and reads the header stamp, so it can tell "the base stopped producing" from "the message was late".

  10. ROS 2 delivers /odom to your program

    DDS on the Pi hands the odometry to every program that subscribed.

    Details
    • A new subscriber to /odom is also a new participant that must be introduced to the base. That introduction is what section 02 is about.

  11. Your program reads /odom and corrects

    It knows where the robot is now, compares that with the plan, and sends the next command. The loop repeats about 20 times a second.

    Details
    • The callback stores x, y and yaw. The 20 Hz loop (one cycle every 50 ms) checks safety, then publishes the next velocity (motion program design).
    • If the stored odometry is older than 0.3 s the program publishes zero velocity and waits. If there is none for 2.0 s it aborts. See section 03.
02

When the base pauses

measured seen in a recording inferred a reading of the numbers, not tested directly not proven one run or open

What was seen measured

  • Now and then every topic from the base stops at once, for 1 to 12 s. That includes /odom, /tf, /imu and /wheel_status.
  • The header stamps stop too. So the base produced nothing; the messages were not just late on the way.
  • Ping from the Pi to the base gets slower during the stall (19.5 to 73.5 ms in the join runs, against a median of 0.5 ms).
  • It is not the Wi-Fi (no errors or drops) and not the Pi (CPU at most 61 % in the first recording).
  • The first sighting was a pause of 0.4 to 1.0 s when the wheels start (TB-15). A pause of 3.16 s aborted a drive on 2026-10-24 (the program's limit is 2.0 s).

The experiment measured

Robot docked, no motion, home Wi-Fi. A recording of /odom and /dock_status ran for 720 s. After a 120 s quiet start, a new ROS 2 program joined the network every 60 s, 8 times, and the recording showed which joins were followed by a stall.

Bare node, 5 s3 of 82.46 s
ros2 topic list --no-daemon1 of 80.26 s
Node subscribing to /odom, 5 s5 of 810.87 s

A program that subscribes to /odom triggers stalls more often and for much longer than a bare node. That is what every motion program does. One run of each, one robot, so treat the counts as a pattern, not a rate. Stalls began 0.8 to 14.7 s after the subscriber started, and each cluster had ended by about 17 s after it.

Likely cause inferred

The base is a small computer and it is already busy. Docked and doing nothing it uses about half its CPU (mean 52 to 56 %). Each new ROS 2 program on the Pi announces itself, and the base has to answer and match its topics. That is called discovery. The numbers fit this: stalls start soon after a join, a program with more topics stalls the base more, and the base itself stops producing. iRobot's own issue tracker describes the same behaviour (create3_docs issue 381). It has not been proven here. It also does not explain why the /odom subscriber is so much worse than a bare node.

What the programs do about it measured

Since the stall follows the program's own start, the motion programs now wait before the first move: at least 20 s after they started, and 5 s of steady /odom (no gap over 0.3 s), with a 30 s timeout. In 10 supervised motion starts with this check, all 10 completed and none aborted. The two longest stalls of that test (9.8 s and 4.4 s) came about 9 s after those programs started, while they were still waiting, so the robot stood still through them. The cost is about 20 s per run (20.0 to 22.5 s). Two runs still had a short pause at motion start (0.52 s and 0.79 s). The 0.3 s hold covers those. Short start pauses are not gone, and the target of no gap over 0.3 s across 10 starts is not met.

The newest result one run, not proof

On 2026-10-24 the base's leftover Wi-Fi search was removed (change R19). The base had no network address but kept scanning for a saved network it could not find, with a scan and a failed address request about every 7.5 s. The TurtleBot 4 manual keeps the base off Wi-Fi anyway. In one repeat of the /odom-subscriber join test, 0 of 8 joins were followed by a stall. There was one unrelated 1.27 s pause later in the run, not after a join. Before R19 the same test gave 5 of 8 and 10.87 s.

Read this carefully. One run is not enough to say R19 fixed it: the earlier stalls also came and went between runs. The recording and write-up are in ROADMAP.md (TB-25, "change A applied (R19) and join test") and MAINTENANCE.md. A second option, TurtleBot 4 discovery server mode, is proposed (ROADMAP, TB-25 change B) but not applied. It would change how every ROS 2 program on the robot finds the others, so it needs the maintainer's go-ahead.
03

What this means for your program

Why a closed-loop program holds still when /odom is late

A closed-loop program decides each next command from where the robot is. If the position is old, the decision is a guess, and the robot may overshoot. So every 50 ms cycle the program checks how old its last odometry is.

  • Older than 0.3 s: publish zero velocity and wait for fresh odometry. The segment carries on afterwards.
  • None for 2.0 s: abort. This is a safety stop. Do not raise the limit without a decision, because the longest stall seen was 3.16 s at motion start and 10.87 s in the join test.

Why a program waits at the start

The program's own start is a join. If it moved at once, a stall of several seconds could land right at motion start and abort the run. Waiting for 20 s and 5 s of steady /odom lets the base settle first. You will see a line like odometry steady for 5.0 s, 20.3 s after start. It is not stuck.
