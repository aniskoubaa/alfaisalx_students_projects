04

Likely causes

A diagnosis from the evidence above, most likely first. None of the three is confirmed.

1. Wi-Fi power saving most likely

Power saving is on by default in Ubuntu, and the robot's Students profile (written on 2026-10-03 by write_keyfile.py) sets no value. With it on, the Pi stays associated with the access point but stops answering incoming connections most of the time.

Fits: no disconnects in the robot's logs, a healthy laptop Wi-Fi, and short answer windows. Check: TB-20 step 2.

2. mDNS on campus names only

turtlebot4.local depends on mDNS, which is unreliable on the campus Wi-Fi. This explains the name failures, not the failures by address.

Avoid it: use the address on the robot's display, for example ssh ubuntu@10.87.10.205.

3. Roaming while driving

Campus access points move the robot between them, which drops SSH while the robot drives. Known since 2026-10-03.

Avoid it: run motion programs detached (setsid nohup), so they keep going when SSH drops.

05

Proposed fix for cause 1

proposed, not applied Run in a terminal on the robot by a person who knows the ubuntu password (sudo asks for it). Connect by the display address first, retrying if needed.

sudo nmcli connection modify Students 802-11-wireless.powersave 2
sudo nmcli connection up Students
Verifynmcli -g 802-11-wireless.powersave connection show Students should print the value for "disable", 2. Then check from a laptop that the robot keeps answering over a longer time (TB-20: 30 attempts over 30 minutes, on two days).
UndoThe same command with powersave 0 (the default): sudo nmcli connection modify Students 802-11-wireless.powersave 0, then sudo nmcli connection up Students.
RiskThe Wi-Fi reconnects, so SSH may drop for a few seconds. No reboot. If the session drops after the first command, log in again and run the second.
RecordWhen applied: add it to the MAINTENANCE.md change register as R14, with the date, and update the incident and Known issues.
If it does not helpRecord that cause 1 is ruled out, read the robot's NetworkManager log during a drop, and consider the lab router (section 08).
06

Workarounds that worked

  1. Connect by IP address. Read the address on the robot's display and use it instead of turtlebot4.local, for example ssh ubuntu@10.87.10.205.
  2. Retry in a loop. The robot answers in short windows, so keep trying. These loops reconnect until you log out normally (ssh exits with 255 when it cannot connect or loses the connection). Set up key login first; press Ctrl+C to stop trying.
# macOS and Linux (also Git Bash on Windows)
while true; do ssh -o ConnectTimeout=5 -o ServerAliveInterval=10 ubuntu@10.87.10.205; [ $? -ne 255 ] && break; sleep 5; done
# Windows PowerShell
while ($true) { ssh -o ConnectTimeout=5 -o ServerAliveInterval=10 ubuntu@10.87.10.205; if ($LASTEXITCODE -ne 255) { break }; Start-Sleep 5 }
  1. The robot's own access point. When the display shows 10.42.0.1, join Turtlebot4. To keep internet at the same time the laptop needs a second Wi-Fi adapter (or Ethernet, or phone tethering).

Step-by-step instructions for users: HOW-TO-CONNECT.md, Troubleshooting.

08

Proposal: put the robot on the lab router

proposal, not done A robot change that needs sudo. The full steps, with commands, are in ROADMAP.md, TB-21. First decide, using the result of the power-saving fix, whether staying on Students is enough.

  1. Secure the router

    TB-22 first: admin login changed, admin page LAN-only. Read the exact SSID and the robot's Wi-Fi hardware address.

  2. Fixed address

    A DHCP reservation for the robot on the router (check that the WRT54G firmware offers it).

  3. New Wi-Fi profile on the robot

    A NetworkManager profile for the lab router with a higher autoconnect priority than Students (10), for example 20. The Wi-Fi password is typed at a hidden prompt, as for Students. The Turtlebot4 access point stays as the last fallback.

  4. Test with a way back

    Try it once with autoconnect off, ideally with a scripted test phase that returns to Students by itself, as on 2026-10-03.

  5. Check and record

    Same address after reboots, fallback to Students with the router off, SSH stable for 30 minutes, /scan rate on a laptop. Record the change in MAINTENANCE.md with verify and undo.

Verify: nmcli -t -f NAME,DEVICE connection show --active shows the lab profile on wlan0, and ip -4 -br addr show wlan0 shows the reserved 192.168.1.x address. Undo: sudo nmcli connection delete "<lab SSID>"; the robot returns to Students; then remove the reservation on the router.
