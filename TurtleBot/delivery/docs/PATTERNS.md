# Patterns from open-source robot applications

Date of study: 2026-11-05. Scope: the supervised food delivery program in `TurtleBot/delivery/` (Nav2 1.3.2, ROS 2 Jazzy, one TurtleBot 4).

## Introduction

This note records what several public robot projects actually do, taken from their source files on GitHub (not from documentation pages or marketing), and compares each pattern with what `delivery_core.py`, `delivery_mission.py`, `config/nav2_delivery.yaml` and the CI workflow already have. The downloaded files were read as data only; nothing was built or run. They are kept locally in the scratchpad folder `research\` (subfolders `tb4`, `rmf`, `nav2`, `prod`, `mission`) and are not part of this repository.

What the delivery program already has, so that it is not proposed again: a pure state machine with a fake-robot test suite (`test_delivery_mission.py`), preflight checks, a steady-odometry gate, stale odometry and stale lidar holds with a limit, one retry per leg that sends only the poses not yet reached, a button hand-off with timeouts, battery alarm, hazard latch, a stop file and signal handling, a line-buffered event log, cancel and stop on every exit path, a speed-capped MPPI controller, collision monitor with a footprint approach polygon, and an offline CI job (`.github/workflows/turtlebot-tests.yml`).

## What each source really does

All URLs use the `jazzy` branch unless stated. Branch heads are newer than the installed Nav2 1.3.2, so details may differ on the robot (see "What could not be verified").

1. **turtlebot4_tutorials** (`turtlebot4_python_tutorials/turtlebot4_python_tutorials/`):
   - `mail_delivery.py` (101 lines): docks if not docked, sets the initial pose to (0, 0), waits for Nav2, undocks, then loops on a terminal menu (`input()`) and calls `startToPose` for the chosen goal. It does not check the navigation result, has no timeout, no battery check, no hand-off step and does not dock at the end. It is a demo, not a mission.
   - `patrol_loop.py` (149 lines): a separate battery-monitor node in a thread with a lock; thresholds 0.95 (resume), 0.20 (go charge), 0.10 (stop). On low battery it navigates to a pose in front of the dock, docks, checks `getDockedStatus()`, waits until 95 % and undocks. Patrol goals are hard-coded and the result of each goal is again not checked. Useful idea: charge to a high threshold (hysteresis) before resuming.
2. **Open-RMF rmf_demos and friends**:
   - `rmf_demos_tasks/rmf_demos_tasks/dispatch_delivery.py`: builds a JSON task request. One pickup and one dropoff gives category `delivery`; several give a `compose` task with `pickup` and `dropoff` phases. Each phase has `place`, `handler` (the dispenser or ingestor name) and a `payload` list of `{sku, quantity}`.
   - `rmf_demos_fleet_adapter/rmf_demos_fleet_adapter/fleet_adapter.py` and `RobotClientAPI.py`: the adapter talks to a fleet manager over HTTP with a 5 s timeout. Every call returns a three-valued result (`SUCCESS`, `RETRY`, `IMPOSSIBLE`). `attempt_cmd_until_success` repeats a command every second in a thread until it is accepted or cancelled. Docking falls back to plain navigation when the dock name is unknown. Robot state (position, map, battery state of charge) is polled and fed to the fleet.
   - `rmf_demos/config/office/tinyRobot_config.yaml`: per-fleet limits, battery model, `recharge_threshold: 0.10`, `recharge_soc: 1.0`, `finishing_request: park`, `reassign_task_interval: 120`.
   - Hand-off (in `rmf_simulation`, `rmf_robot_sim_common/src/dispenser_common.cpp`, message definitions in `rmf_internal_msgs/rmf_dispenser_msgs`): a request carries a `request_guid` and a `target_guid`; the dispenser reports state `IDLE`, `BUSY` or `OFFLINE`, and answers with `ACKNOWLEDGED`, then `SUCCESS` or `FAILED`. It remembers past request ids, so a repeated request gets the same answer (idempotent). The ingestor has the same shape; its file was not read.
   - CI: `rmf_demos/.github/workflows/build.yaml` calls a shared reusable workflow (`open-rmf/rmf_ci_templates`) on pull request and on a nightly schedule, with a Jazzy and Noble matrix.
3. **Nav2** (`ros-navigation/navigation2`):
   - `nav2_system_tests/` (`src/system/test_system_launch.py`, `src/system_failure/`, `src/updown/`, `src/waypoint_follower/`): each test launches a headless Gazebo server (`gz sim -r -s`), spawns a TurtleBot 3, includes the real `bringup_launch.py` with a rewritten params file, then runs a tester node as a second process through `launch_testing`. The README lists the families: navigate to pose, through poses, waypoints, random planning, lifecycle up/down repeated, keepout and speed zones, behaviours, and recorded system failures. `system_failure/tester_node.py` shuts down the lifecycle managers and expects the goal to fail ("Goal failed, as expected").
   - `nav2_collision_monitor/` and `nav2_bringup/params/nav2_params.yaml` (lines 374 to 403): same single `FootprintApproach` polygon with `time_before_collision: 1.2` as our file; `source_timeout: 1.0`, `stop_pub_timeout: 2.0`. The node can publish `nav2_msgs/CollisionMonitorState` (`action_type` STOP=1, SLOWDOWN=2, APPROACH=3, LIMIT=4, and `polygon_name`) on `state_topic`; our file already sets `state_topic: collision_monitor_state`, but nothing in the mission reads it.
   - `nav2_docking/opennav_docking/src/docking_server.cpp`: `max_retries: 3`; on a failed attempt it logs a warning and retries, and fails after the limit. Parameters worth noting: `dock_prestaging_tolerance: 0.5`, `staging_x_offset: -0.7`, `dock_approach_timeout: 30`, `wait_charge_timeout: 5`. We use the Create 3 dock action, not this server (it is not in the installed package list from fact sheet 2).
   - `nav2_bt_navigator/behavior_trees/navigate_through_poses_w_replanning_and_recovery.xml` (the default we run, because our yaml leaves `default_nav_through_poses_bt_xml` unset): replans every 3 s (`RateController hz=0.333`), drops reached goals within 0.7 m, clears the relevant costmap once on a planner or controller error, and wraps everything in `RecoveryNode number_of_retries="6"`. Its round-robin recovery is: clear both costmaps, Spin 1.57 rad, Wait 5 s, BackUp 0.30 m at 0.15 m/s.
   - `nav2_lifecycle_manager/src/lifecycle_manager.cpp`: defaults `bond_timeout` 4.0 s, `bond_respawn_max_duration` 10.0 s, `attempt_respawn_reconnection` true; heartbeat period 0.10 s, check timer 200 ms. If one managed node misses its heartbeat, the manager performs a hard reset of all managed nodes (everything goes inactive) and then waits up to the respawn duration for the server to return. It also exposes `is_active` (std_srvs/Trigger) and a diagnostic named "Nav2 Health".
   - `nav2_loopback_sim` exists on the Jazzy branch (a node that turns `cmd_vel` into odometry, TF and a synthetic scan, so Nav2 can run with no simulator). It is not installed on the robot.
4. **Production style repositories**:
   - `ros-industrial/industrial_ci` (`.github/workflows/main.yml`, `doc/index.rst`): CI runs inside Docker, configured by environment variables (`DOCKER_IMAGE`, `UPSTREAM_WORKSPACE`, `AFTER_SCRIPT`, `NOT_TEST_BUILD`), a distro matrix, a nightly schedule, `paths-ignore` for docs, and a separate `shellcheck` job over all its shell scripts.
   - `clearpathrobotics/clearpath_robot` (README): one `robot.yaml` is parsed by `clearpath_config`, a generator writes the launch and parameter files into `/etc/clearpath`, and `systemd` units (`clearpath-robot.service` with child services) start the robot on boot; helper scripts include `generate`, `install`, `check` and a diagnostics grabber. Generated output is versioned in a separate `clearpath_generator_tests` repository and compared in CI (golden-file test). `clearpath_config` has pytest unit tests mirroring its package layout.
   - `ros/diagnostics` `diagnostic_aggregator` (README): turns the flat `/diagnostics` stream into a grouped `/diagnostics_agg` using path-prefix analyzers defined in YAML.
   - Autoware (`autoware_universe/system/`): `autoware_diagnostic_graph_aggregator` builds a directed graph of AND and OR units over `/diagnostics` and publishes which operation modes are currently available; `autoware_mrm_handler` is a small state machine that picks a minimal-risk manoeuvre (emergency stop, comfortable stop, pull over) from that availability. I read the READMEs; the graph YAML example and handler source were not read.
5. **Mission-layer examples**:
   - `py_trees_ros_tutorials/seven_docking_cancelling_failing.py` (devel branch): a parallel root with topic-to-blackboard behaviours, a battery emergency guard, a cancel event, and a rule stated in its docstring that application failure is recorded by behaviours (results are written to the blackboard and reported after the post-failure actions), not by the tree status.
   - `nav2_simple_commander/demo_security.py`: `goThroughPoses` in a loop; inside the wait loop it reads feedback and calls `cancelTask()` when `navigation_time` exceeds 180 s; the result (succeeded, canceled, failed) decides what happens next.
   - `nav2_waypoint_follower` (`waypoint_follower.cpp`, `plugins/wait_at_waypoint.cpp`, `plugins/input_at_waypoint.cpp`): a task-executor plugin runs at each waypoint. `WaitAtWaypoint` pauses for a set time; `InputAtWaypoint` waits for a message on a topic with a timeout, which is the same idea as our button wait. `stop_on_failure` and `loop_rate` are parameters.
   - BehaviorTree.CPP headers `decorators/retry_node.h`, `timeout_node.h`, `controls/reactive_sequence.h`: retry N times, timeout wrapper, and a sequence that re-evaluates its earlier children every tick. Only headers and comments were read.

## Top changes to make now

Ranked by risk removed per hour of work. Each can be done and tested offline before it touches the robot.

1. **Replace the default recovery tree with a delivery tree.** Copy the upstream through-poses tree into `delivery/config/bt_through_poses_delivery.xml`; in the `RoundRobin` keep the clearing sequence and `Wait 5.0`, delete `Spin` and `BackUp`; lower the outer `number_of_retries` from 6 to 3; keep replanning and `RemovePassedGoals` as they are. Point `bt_navigator.default_nav_through_poses_bt_xml` at it in `nav2_delivery.yaml`. The mission already retries a failed leg once after clearing the costmaps, so the tree needs only to fail fast. Extend `test_delivery_config.py` to parse the XML, require that every node name is one the default tree uses, and require that the file path in the yaml exists. Do not use the file until the same node names are confirmed against the installed tree on the robot (read-only `cat` of the installed file).
2. **Nav2 liveness check during legs.** Add `nav_alive()` to the `Robot` interface in `delivery_core.py` (returns True, False, or None when unknown; the base class returns True so existing fakes keep working). In `delivery_mission.py` implement it by calling `lifecycle_manager_navigation/is_active` at most once a second (non-blocking, with a 1 s timeout). In `_leg`, if it returns False twice in a row: cancel, stop, alarm "Nav2 stopped" (no retry, because a bond break resets every Nav2 node). Add a fake-robot test next to `stale_between`. Optional second step after reading the robot's launch file: set `bond_timeout` larger than 4.0 s only if the launch passes parameters to the lifecycle manager (not verified).
3. **React to the collision monitor.** Subscribe to `collision_monitor_state` in `delivery_mission.py` and expose `blocked_for()` (seconds the last STOP or APPROACH state has lasted; clears when `DO_NOTHING` arrives). In `_leg`, after 8 s blocked show "Please step aside"; after a limit (new setting `blocked_alarm_s`, start at 45 s) alarm "Path blocked" instead of waiting for the leg timeout. Pause, do not count it as a failure or a retry. Test with a fake robot that reports blocked intervals. Message field names are from the Jazzy branch; confirm with `ros2 interface show nav2_msgs/msg/CollisionMonitorState` first.
4. **One dock retry from a staging pose.** Add an optional `dock_staging` pose to the route (default: dock pose moved 0.7 m back along its heading, the offset `opennav_docking` uses) and to `plan_route.py` output. In `_dock`, if the dock action fails or `/dock_status` does not confirm: send one `go_through([staging])` leg, wait for success, then dock again; a second failure is the existing alarm. Keep the low-battery exception in `_dock`. Add tests for: first dock fails and second succeeds; both fail; staging leg fails.
5. **Run identifier and result line in the log.** Generate a short run id (date and time) at the start of `DeliveryMission.run`, put it in the first and last events and in `MissionResult`, and make the final log line a single parseable summary (`outcome`, `code`, `reason`, `food`, `received`, leg times). This is the useful part of the dispenser/ingestor request-id pattern and costs about twenty lines. It also gives the weekly report one line per run.
6. **CI hardening that needs no new package.** In `.github/workflows/turtlebot-tests.yml`: (a) add a `shellcheck` step over `TurtleBot/delivery/robot/*.sh` and `TurtleBot/delivery/phase0/*.sh` (shellcheck is normally present on the `ubuntu-24.04` runner; check the first run), fixing or annotating what it reports; (b) add a weekly `schedule` trigger next to push and pull request; (c) add a step that fails if `use_sim_time: true` appears anywhere under `TurtleBot/delivery/config/` (the installed TurtleBot 4 files have it, fact sheet 2) if `test_delivery_config.py` does not already do so.

Not in the top six but worth keeping in view: a CI container job using `ros:jazzy` with Nav2 and the loopback simulator, running the real mission adapter against a map (the `nav2_system_tests` pattern), and grouping the preflight and `_tick` checks into a single `health()` result.

## What could not be verified

- No robot access: the installed `bt_navigator`, behavior tree files, lifecycle manager parameters and the TurtleBot 4 launch files were not read. Changes 1, 2 and 3 need a read-only look at the installed files first. In particular I do not know if the installed launch passes a `bond_timeout` to the lifecycle manager, nor which behavior tree file is actually loaded.
- GitHub `jazzy` branch heads were read, not the 1.3.2 release tag. Defaults such as `bond_timeout` 4.0, the `is_active` service and the `CollisionMonitorState` fields could differ in 1.3.2. The "Nav2 Health" diagnostic in the lifecycle manager may be newer than 1.3.2.
- It was not tested that skipping Spin and BackUp is safe on the real route, or that the 3-retry setting gives good behavior; it needs a trial with the robot in the safe zone.
- Open-RMF: the dispenser file and message definitions were read; the ingestor, the task-side phases that wait for the result, and `RobotCommandHandle` (path 404) were not. The statement that task phases wait for `SUCCESS` or `FAILED` comes from the message definitions, not from the task code.
- Autoware and Clearpath: only READMEs and directory listings were read, not the implementation. The name of Clearpath's diagnostics helper script is cut off in the README table and is not stated here.
- BehaviorTree.CPP and py_trees: only headers, docstrings and one tutorial were read.
- Nav2 system tests: the structure and the launch file were read; the test results were not reproduced, and the claim that `system_failure` expects a failed goal comes from the log text in `tester_node.py`.
- shellcheck being preinstalled on the GitHub runner was not checked.
