ROS 2 mobile robot — field reference

TurtleBot 4

The robot your professor handed you is a stack, not a single gadget — an iRobot drive base, a Raspberry Pi, a spinning lidar, a depth camera, and ROS 2 tying all of it together. Here's what each layer does and how to get it moving.

01

What it actually is

TurtleBot 4 isn't built by one company. Open Robotics designed the reference platform; Clearpath Robotics manufactures and sells it; the wheeled base underneath is an actual iRobot Create 3 — the same drivetrain family as a Roomba, repurposed as a programmable robot. ROS 2 (Robot Operating System 2) is the software layer that makes every part talk to every other part, and to your code.

It ships in two builds. Check which one your lab has before you go looking for hardware that isn't there:

StandardLite
CameraOAK-D Pro — longer range, more onboard AIOAK-D Lite — shorter range, lighter compute
EnclosureFull stacked shell with light stripOpen frame, easier to bolt things onto
Typical useStandard course kit, closer to "out of the box"Cheaper fleets, projects that add custom hardware
02

Why this platform, specifically

Whatever the assignment is — mapping, navigation, obstacle avoidance, a custom node — the reason it runs on real TurtleBot hardware instead of simulation alone comes down to four things:

  • ROS 2 is what the industry actually runs. This isn't a classroom dialect — code you write here looks like code written at an actual robotics company.
  • Sim-to-real is a real workflow. Gazebo simulates the same robot model and the same topic names, so you can develop and debug an algorithm for free, then point it at the physical robot with little to no code change.
  • Real sensors are noisy on purpose. A simulated lidar scan is clean; a real RPLIDAR gives you dropouts, reflective surfaces, and drift. That mess is the actual lesson — it's what separates an algorithm that works on paper from one that works.
  • It's built to survive students. Bump sensors, cliff sensors, and a top speed under 1 m/s mean a bad line of code produces a stall against a wall, not a broken robot.
03

Hardware

Four subsystems, stacked on top of each other. Each one publishes or consumes ROS 2 topics — that thread is what ties the rest of this guide together.

Mobile baseiRobot Create 3 — differential drive, wheel encoders, bump / cliff / IR sensors, auto-dock charging, RGB light ring, speaker.
ComputeRaspberry Pi 4B, running Ubuntu and ROS 2. Confirm the exact distro your lab image uses — most kits shipped on Humble, some labs have since moved to a newer LTS release.
LidarSlamtec RPLIDAR A1 — continuously spinning, 360° coverage, roughly 12 m range. This is what SLAM and obstacle avoidance read from.
CameraOAK-D Pro / OAK-D Lite (Luxonis) — stereo depth plus RGB, with an onboard VPU that can run AI inference without taxing the Pi.
IMUBuilt into the Create 3 base — feeds orientation into odometry, no separate module to wire up.
RuntimeRoughly a couple of hours of active driving per charge, then it can return to its dock on its own.
ConnectivityWi-Fi only. Most coursework runs your code on a separate networked "remote PC," though you can also SSH straight onto the robot's Pi.
04

The ROS 2 stack

Every piece of hardware above talks to the rest of the system by publishing or subscribing to a named topic. This publish/subscribe graph is ROS 2 — the TurtleBot is just a robot to learn it on.

Packages you'll actually launch

turtlebot4_vizPre-built RViz2 configuration for the robot's sensors.
turtlebot4_navigationLaunch files for SLAM mapping and for running Nav2 against a saved map.
nav2 (nav2_bringup)The navigation stack itself — planners, controllers, costmaps, recovery behaviors.
slam_toolboxBuilds an occupancy-grid map from lidar scans as you drive.
irobot_create_msgsMessage and action types specific to the Create 3 base (dock, undock, bump events).
05

Concepts glossary

The vocabulary that shows up in every assignment, regardless of topic:

Node
One running program. A lidar driver is a node; your obstacle-avoidance script is a node. A running robot is dozens of nodes at once.
Topic
A named, typed stream of messages any node can publish to or subscribe to, with no direct link between them. /scan, /odom, /cmd_vel are topics.
Service
A one-shot request/response call between exactly two nodes — "clear the costmap," for example.
Action
Like a service, but for something that takes time and reports progress. navigate_to_pose is an action, so you get feedback while the robot is still driving there, not just a final result.
TF (transform tree)
The chain of coordinate frames — map → odom → base_link → laser_frame — that lets ROS 2 answer "where is this lidar point, in map coordinates?" Most navigation bugs trace back to a broken or missing transform.
Launch file
A script that starts a whole set of nodes with matching configuration at once, instead of running each by hand.
Package
The unit ROS 2 code ships in: a folder with a manifest, some nodes, and usually a launch file.
ROS_DOMAIN_ID
An environment variable that has to match between your remote PC and the robot or they never see each other's topics — the single most common "why isn't anything showing up" bug.
06

Getting started

The order actually matters here — each step is what you use to verify the previous one worked.

  1. Match your remote PC to the robot

    Same ROS 2 distro installed, same ROS_DOMAIN_ID exported in your shell. Nothing else works until this is true.

  2. Drive it by hand

    teleop_twist_keyboard publishes to /cmd_vel from your keyboard. If the robot moves, your networking is correct — that's the whole point of this step.

  3. Look at what it senses

    Open RViz2 and add the /scan, /odom, and camera displays. This is how you'll debug everything downstream — trust the visualization over your assumptions about what the sensors "should" see.

  4. Build a map

    Drive the robot around the space with SLAM Toolbox running; it stitches consecutive lidar scans into an occupancy grid.

  5. Save the map

    Write it to disk once it's complete. Nav2 needs a finished map, not a live SLAM session, to plan routes.

  6. Let Nav2 drive

    Launch navigation against the saved map, set an estimated starting pose, then send a goal pose in RViz2 and watch it plan a path and avoid obstacles along the way.

  7. Write your own node

    Usually the actual assignment: a Python (rclpy) or C++ (rclcpp) node that subscribes to sensor topics, does something with the data, and publishes back to /cmd_vel.

Before you start: confirm your lab's ROS 2 distro and whether you're expected to code on the robot's own Pi or on a separate remote PC — that answer changes almost every command below.
07

What the assignment probably is

Coursework built on TurtleBot 4 tends to fall into one of these, whatever the specific brief says:

Reactive control

Read /scan directly, react with no map involved — wall following, obstacle avoidance, a bang-bang or PID controller on distance.

Mapping

Run SLAM Toolbox, evaluate the resulting map quality, tune scan-matching parameters.

Autonomous navigation

Work inside Nav2 — costmaps, planners, waypoint sequences, sometimes a custom recovery behavior.

Perception

Use the OAK-D's RGB or depth stream — object detection, color tracking, depth-based avoidance.

Custom node development

The "write ROS 2 code" assignment underlying most of the above: subscribe, compute, publish, on a timer or callback.

Command reference

ros2 topic listSee every live topic on the graph.
ros2 topic echo /scanPrint live lidar messages to the terminal.
ros2 topic hz /scanCheck how fast a topic is actually publishing.
ros2 node listSee every node currently running.
ros2 run teleop_twist_keyboard teleop_twist_keyboardDrive the robot with your keyboard.
ros2 launch turtlebot4_viz view_robot.launch.pyOpen RViz2 pre-configured for the robot's sensors.
ros2 launch turtlebot4_navigation slam.launch.pyStart SLAM mapping.
ros2 run nav2_map_server map_saver_cli -f my_mapSave the current map to disk.
ros2 launch turtlebot4_navigation nav2.launch.pyStart Nav2 against a saved map.
